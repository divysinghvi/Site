## UNVERIFIED

- Official SQLite documentation pages (`withoutrowid.html`, `wal.html`, `lang_vacuum.html`, `pragma.html`) — sqlite.org is blocked. Everything the plan relies on (WAL persistence, `busy_timeout` wait, WITHOUT ROWID composite keys, upsert, `RETURNING`, `VACUUM INTO`, checkpoint) was verified **empirically** with the pinned driver (S3–S7). The general statement "WITHOUT ROWID is best for tables with small rows" is applied as a design rule but its documentary wording is not quoted.
- Whether `contributionCalendar` / `commitContributionsByRepository` for the token owner include **private-repository** activity without the profile setting "include private contributions" being enabled. The schema only documents `restrictedContributionsCount` ("contributions … that the viewer cannot access") and `isRestricted`. The collector logs `totalCommitContributions`, calendar total, `restrictedContributionsCount` and `hasAnyRestrictedContributions` on every run so this is settled empirically at Phase 1 (`divy collect --once --only github`).
- The maximum accepted value of `commitContributionsByRepository(maxRepositories:)` (schema gives only the default 25). The plan uses 100 and checks `totalRepositoriesWithContributedCommits` to detect truncation.
- Fine-grained PAT specifics for **organization-owned private** repositories (org approval policy, required "Pull requests: read"/"Contents: read" permissions). The docs fetched state only that fine-grained PATs "include read access to public repositories". The plan recommends a classic PAT (`repo`, `read:user`) when private counts are wanted.
