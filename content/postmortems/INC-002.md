## Summary

The host that runs the reverse proxy (`proxy-host`) also ran a self-hosted Sentry deployment of
roughly 65 containers. Under load, Sentry's containers consumed most of the host's RAM and pushed
the rest into swap. Once swap saturated, memory pressure cascaded: the proxy and the other
services sharing the host slowed down and became intermittently unresponsive.

The response was triage (find which containers held the memory), profiling (measure what each
part of Sentry actually needed), and right-sizing: Sentry was reduced to an errors-only profile
that drops the services Gradr did not use, bringing the host back well under its memory budget.

- Trigger: memory growth in Sentry's containers over time — TODO(divy): what tipped it (traffic, ingest backlog, a Sentry upgrade?)
- Fault: a ~65-container stack co-located with the proxy on one host with no per-service memory limits
- Fix: right-sized Sentry to an errors-only profile

## Root cause

A default self-hosted Sentry installation runs a large number of services — ingest, processing,
storage and query backends for every product surface, not just error tracking. Deployed on the
same host as the reverse proxy, with no memory limits per service, that footprint grew until it
exceeded physical RAM. Swap absorbed the overflow only until it, too, was full; from then on the
kernel's memory pressure affected every process on the host, including the proxy in front of
production traffic.

Contributing factors:

- Co-location: the proxy shared a host with the heaviest component of the observability stack.
- No cgroup memory limits on Sentry's containers, so nothing bounded the blast radius to Sentry itself.
- Swap masked the growth: the host looked "fine" on free RAM alone until swap was exhausted.
- The default profile was never trimmed to the features actually in use.

## Lessons

- Defaults are sized for the vendor's product, not for your workload. Trim to the features you use before the host makes you.
- Swap is not headroom; it is a delay between "over budget" and "outage". Alert on swap usage, not only on free RAM.
- The reverse proxy is the one process that must never compete for memory. Keep the edge isolated from batch-heavy neighbours.
- Per-container limits turn a host-wide cascade into a single-service failure, which is the failure you can page on and debug.
