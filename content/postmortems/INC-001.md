## Summary

After a reboot of the host running the Gradr application stack, the application containers came up
before the secrets-injection sidecar had written the `.env` file they read at boot. The containers
started with an empty or missing environment, could not reach Supabase, and the Supabase-backed
service was down until the ordering problem was understood and fixed.

The fix was structural, not a restart: app containers now start only after the sidecar reports
healthy, and the healthcheck is gated on the secrets actually being present.

- Trigger: host reboot (TODO(divy): planned maintenance, provider reboot, or kernel update?)
- Fault: no startup dependency between the secrets sidecar and its consumers
- Fix: startup ordering + healthcheck gating

## Root cause

The application containers and the secrets-injection sidecar had no ordering relationship. Both
were started by the container runtime at boot; whichever won the race determined whether `.env`
existed when the apps read it. Under normal operation the race was invisible because the sidecar
had written the file long ago and only the apps were restarted. A cold boot of the whole host
exposed it: the apps read their environment exactly once, at process start, and never re-read it.

Contributing factors:

- The apps treated a missing `.env` as "no configuration" rather than as a fatal startup error, so they came up in a broken state instead of crash-looping until the file appeared.
- Nothing in the boot path verified that secrets were present before declaring a container healthy.
- Cold boots had not been rehearsed; rolling restarts were the only tested restart path.

## Lessons

- Reboots are a deploy. Test cold start, not just rolling restarts.
- "Reads config once at boot" is a dependency on everything that produces that config; make the dependency explicit in the orchestrator.
- A healthcheck that only says "the process is up" hides the failure that matters. Check the thing the service needs (here: secrets present) rather than the process.
- Running degraded is worse than crash-looping: a crash loop is visible and self-heals once the dependency appears.
