## Summary

Outbound email from self-hosted Sentry was failing. Sentry uses email for alert notifications,
team invites and account flows, so the failure meant error alerts were not reaching anyone by
mail and new members could not be invited. The fix had two parts: the SMTP relay was switched to
Resend on port 2465, and the from-address configuration — which the previous setup had wrong —
was corrected so the relay would accept and deliver the mail.

- Trigger: TODO(divy) (relay change, provider policy, a Sentry upgrade that changed mail settings?)
- Fault: outbound SMTP path broken; from-address misconfigured
- Fix: Resend as the relay on 2465 + correct from-address

## Root cause

Two independent problems overlapped, which is why the first fix alone was not enough:

1. The outbound SMTP path Sentry was using did not work — TODO(divy): the previous relay and the failure reason.
2. The configured from-address was not one the relay would send on behalf of, so even a working relay rejected the mail.

Because Sentry sends alert email asynchronously and does not surface delivery failures in the UI,
neither problem produced a visible error where anyone was looking.

Contributing factors:

- Email delivery had no monitoring of its own; it was assumed to work because it had once.
- The from-address was configured in more than one place (TODO(divy): confirm), so a partial edit left them inconsistent.

## Lessons

- An alerting channel that fails silently is an outage of the alerting system. Monitor the channel, not just the things it reports on.
- Fix one variable at a time and re-test: the relay change looked like a failure until the second cause (from-address) was found.
- Never let one channel be the only path for critical alerts.
- Configuration that lives in several places drifts; keep the source of truth in one file and reference it.
