## Summary

Two opposite defects were degrading the error-tracking signal in self-hosted Sentry at the same
time. A capture gate in the SDK configuration was silently discarding a class of errors that
included critical infrastructure failures, so the most important events never reached Sentry.
Meanwhile, fingerprinting was unbounded: values that vary per event were ending up in the
grouping key, so one underlying error became a new issue every time it occurred, producing more
than 1000 duplicate issues and burying everything else under noise.

Both were fixed at the source (the gate was corrected so infra errors are captured; grouping was
bounded so one cause maps to one issue) and the alert rules were cleaned up so that what fires is
worth reading.

## Root cause

**Dropped errors.** The capture gate — TODO(divy): a `beforeSend`-style filter, a sample rate, or an
environment/level allow-list — matched more than intended and rejected events that included
critical infrastructure errors. Because dropping is by design silent in the SDK, there was no
metric or log line saying "N events discarded", so the absence of these errors read as "nothing
is wrong".

**Duplicate issues.** Sentry groups events into issues by fingerprint. The fingerprint (or the
message it was derived from) included per-event values — TODO(divy): which ones (IDs, timestamps,
addresses, dynamic paths?) — so events with the same cause never shared a fingerprint. Every
occurrence became a new issue and every new issue could trigger a "new issue" alert.

Contributing factors:

- No test asserted that a known infra error actually reaches Sentry.
- Grouping was left at defaults for error messages that embed variable data.
- Alert rules fired on "new issue" without rate limits, so the duplicates amplified into alert noise.

## Lessons

- Silence is not health. A filter that drops events needs a counter, and the events you care about most need a canary that proves they arrive.
- Grouping is part of the signal. If the fingerprint contains anything that varies per event, the issue list stops meaning anything.
- Alert hygiene is ongoing work: every "new issue" rule should be rate-limited and every alert should be one a person would act on.
- Investigate noise all the way down: the duplicate flood was the symptom that exposed the more dangerous, silent defect.
